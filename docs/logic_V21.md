# 1. 总体逻辑：事件驱动的持续判定闭环

系统不是「监控 --- 报警 ---
结束」的线性流程，而是一个由事件反复唤醒的闭环。输入框传进来的任何信息、任何状态变化（链路故障、审批决策、需求变更、任务与链路登记、修理回执）都被归一成一个事件，事件唤醒
Agent，Agent
读取本体语义与数据库实时数据，重算当前与未来，做前瞻预测，选择动作执行，执行结果写回本体后又成为新的事件------如此递归，直到没有任何新状况需要处理。

> ① 事件产生（输入框四类输入 / 预订事件到点 / 动作执行结果 / 外部回执）
>
> ↓
>
> ② Agent 被唤醒 → 识别事件类型与参数
>
> ↓
>
> ③ 按本体语义定位：需要读取哪些对象与字段（任务 / 链路 / 需求 / 方案 /
> 工单）
>
> ↓
>
> ④ 通过 Skill / MCP 按「本体字段 ↔ 数据库」映射读取实时数据
>
> ↓
>
> ⑤ 逻辑判定：当前占用 / 未来占用 / 容量 / 预警线 / 关键期 / 链路状态
>
> ↓
>
> ⑥ 前瞻推演：在 \[now, now + LOOKAHEAD\] 窗口内逐检查点预测
>
> ↓
>
> ⑦ Agent 选择动作：自动执行，或挂起等待人工审批（60 秒倒计时）
>
> ↓
>
> ⑧ 执行 → 状态写回本体 → 产生新事件 → 回到 ①（递归判定）

**关键设计：动作不是终点，而是新事件的起点。切换完成后、收到修理单后、链路恢复后、新增任务或链路后，都必须再触发一次本体读取判定，确认「还有没有别的状况」。**

# 2. 场景时钟与输入框

## 2.1 实时时钟

场景时钟 1:1 对应演示的真实时间：以启动时刻为 T+0，真实经过 N
分钟就是场景的 T+N。不加速、不减速、不暂停------业务说「15
分钟后」，就是真实世界过了 15 分钟。

  **项**           **取值**                   **说明**
  ---------------- -------------------------- -------------------------------------------------------------------
  基准             T+0                        POST /api/scene/start 时记录真实时刻为锚点 start_wallclock
  单位             分钟（整型）               全部 \*\_min 字段，与真实经过分钟数一致
  推进             固定 1 倍速                不支持调速；真实每过 1 分钟对全部 up 链路执行一次 ACT-02 前瞻扫描
  总长             120 分钟                   由最长任务持续时间（2h）决定，全程真实耗时 2 小时
  挂起             不挂起                     等待审批期间真实时间照常推进
  映射到真实时刻   start_wallclock + N 分钟   看板同时显示相对分钟与真实时刻

**取消挂起后为什么仍不会偷跑：**

> 前瞻提前量 = 30 分钟 （可预警的时间余量）
>
> 人工决策时限 = 60 秒 （模态框倒计时）
>
> 两者相差 30 倍
>
> 本场景：T+20 命中 T+50 的超限风险并弹窗
>
> 最迟 T+21（60 秒到期）方案落地
>
> 距 T+50 真正超限还有 29 分钟
>
> → 无需暂停时间，人工余量充足，时间语义保持干净

兜底规则：若某次预测的超限点距当前不足 60
秒（提前量盖不住决策时限），则不再依赖人工流程，直接按 R3
硬约束------当前占用一旦真实越限立即重新生成方案，杜绝「等人工等到撑爆」的空窗。

## 2.4 预订事件的兑现机制

带「N
分钟后」的时间状语的输入不是立即生效，而是登记为预订事件。预订事件写入
comm_event（event_type = task_booked，occur_min = 生效分钟），occur_min
大于当前场景分钟数即为待兑现。引擎每推进 1
分钟扫描一次，到点兑现为真实事件。

> 登记：POST /api/scene/input {category: notice, payload:
> 50分钟后直播任务需求到6.00G}
>
> → Agent 识别 → SK-10 写入 comm_demand(D-B2, T-B, valid_from_min=50,
> 6.00)
>
> → comm_event(EVT-002, task_booked, occur_min=50, 待兑现)
>
> 兑现：场景时钟推进到 T+50
>
> → 引擎扫描到 occur_min=50 的待兑现事件
>
> → 触发 ACT-02 全局重算（D-B2 此刻开始生效）
>
> → 写 state_changed，事件标记已兑现

默认场景预置的两条外部信息（T+15 线路 1 故障、T+50 直播需求到
6G）走的就是这条路径。

# 3. 核心算法

## 3.1 三个占用口径（必须严格区分）

  **口径**                    **算式**                                                                                                        **用于**
  --------------------------- --------------------------------------------------------------------------------------------------------------- ------------------------------------
  当前占用 current(L, now)    Σ 链路 L 承载任务中，valid_from_min ≤ now \< valid_to_min 的 demand_gbps（valid_to_min 为 NULL 视为持续有效）   看板；容量硬约束兜底
  未来占用 future(L, now)     Σ 链路 L 承载任务各自「最晚一条需求记录」的 demand_gbps（折叠值，不含时间维度）                                 预警线判定（唯一口径）
  预测占用 predicted(L, m′)   在未来确定分钟 m′，Σ 链路 L 承载任务届时生效的 demand_gbps                                                      容量超限判定（前瞻窗口内逐点计算）

**为什么必须区分：**

T+15 故障切换后，L-2H 的折叠未来值已经是 11G，看上去已经超过 10G
容量。但折叠值不携带时间信息------它只说明「终将会到
11G」，不说明「什么时候到
11G」。容量是否构成威胁，取决于到达时刻是否落在可预警的时间窗内。因此容量超限一律由「绑定时刻的预测占用
+ 前瞻窗口」判定，折叠值只用于预警线提示。这是 T+15 只报预警、T+20
才报超限的根本原因。

## 3.2 前瞻扫描与分级窗口

> LOOKAHEAD(L) = max(
>
> comm_link\[L\].lookahead_min, \# 链路级
>
> max(comm_task\[x\].lookahead_min for x in tasks(L)) \# 任务级
>
> ) \# 字段为空时按 30 分钟缺省
>
> M = { d.valid_from_min \| now \< d.valid_from_min \<= now + LOOKAHEAD,
> d 属于 tasks(L) }
>
> ∪ { now + LOOKAHEAD } \# 窗口内无变更点时，至少评估窗口末端
>
> for m\' in sorted(M):
>
> pred = predicted(L, m\')
>
> if pred \> capacity : return OVER_CAPACITY(m\', pred)
>
> if pred \> warning : return WARN(m\', pred)
>
> return OK

分级配置：链路级字段给出该链路的默认提前量，任务级字段可按重要度上调（例如指挥通信任务配
60
分钟）。有效窗口取两者最大值，保证任何重要任务的风险都不会被较短的链路默认值掩盖。本场景三链路三任务均配
30 分钟。

**窗口覆盖验算：**

  **当前分钟**       **前瞻窗口**   **是否含 T-B 的 T+50 变更点**   **窗口内最大预测占用**       **结论**
  ------------------ -------------- ------------------------------- ---------------------------- ---------------------------
  T+15               \[15, 45\]     否                              9G（无变更点，取窗口末端）   不触发超限，仅超预警线
  T+20               \[20, 50\]     是                              11G（3 + 6 + 2）             11G \> 10G → 触发超限预警
  T+21（转备用后）   \[21, 51\]     是                              L-2H 8G；L-3H 3G             均不超限，全部正常
  T+50（需求翻倍）   \[50, 80\]     否（已生效）                    L-2H 8G；L-3H 3G             8G 正好压预警线，正常

## 3.3 判定规则汇总

  **规则**              **条件**                                                **级别**   **处理**
  --------------------- ------------------------------------------------------- ---------- --------------------------------------------------------
  R1 预警线             future(L, now) \> warning_gbps（8G）                    黄色       warn_status = 超预警线；顶部提示条；不生成方案、不挂起
  R2 容量超限（前瞻）   ∃ m′ ∈ 窗口，predicted(L, m′) \> capacity_gbps（10G）   红色       写容量超限告警 + ACT-03 + 挂起审批
  R3 容量硬约束         current(L, now) \> capacity_gbps                        红色       立即置超容量并触发 ACT-03
  R4 链路不可用         oper_state = down                                       红色       ACT-01 迁移任务 + 告知型弹窗
  R5 备用启用           需占用 backup_link_code 指向的备用链路                  橙色       需审批；超时走保守默认
  R6 回迁条件           原链路 oper_state = up 且回迁后不超限                   绿色       ACT-06 自动回迁 + 释放备用
  R7 新对象登记         输入框新增任务或链路                                    绿色       登记后触发 ACT-02 全局重算，校验容量是否仍然满足

注：预警线与容量判定均使用严格大于。故 T+0 与 T+50 时 L-2H 的 8G
都判定为「正常」，与「8G 正好压预警线」的表述一致。

# 4. 动作调度链与递归判定

## 4.1 动作触发关系

  **动作**              **触发条件**                            **执行方式**                   **执行后产生的新事件**
  --------------------- --------------------------------------- ------------------------------ ------------------------------
  ACT-01 自动切换       alarm_injected（link_down）             自动，告知型弹窗               switch_done + 修理请求
  ACT-02 占用与前瞻     任意影响占用的事件；时钟每推进 1 分钟   自动，提示条                   occupancy_exceeded（命中时）
  ACT-03 方案生成       ACT-02 判定超容量                       自动，弹模态框不挂起           plan_generated
  ACT-04 审批决策       存在待审批方案                          需审批，模态框 + 60 秒倒计时   approval_decided + 迁移结果
  ACT-05 修理回执评估   repair_received / repair_finished       自动，提示条                   方案可行性刷新 / 作废
  ACT-06 回迁与释放     link_restored（修复完成）               自动，提示条                   link_restored + 占用重算

输入框的任务与链路登记不对应独立动作：登记后产生 task_added / link_added
事件，由该事件触发 ACT-02 全局重算。若新任务导致容量超限，自然进入
ACT-03 → ACT-04 的既有链路，无需新增动作。

## 4.2 递归判定的终止条件

**每次动作执行后都会再次触发全局判定，因此必须有明确的终止条件，否则会陷入无限循环。终止条件是：本轮判定未命中
R2 / R3 / R4 / R6
中的任何一条，即不存在超限、不存在不可用链路、不存在待回迁任务，且没有新事件入队。此时闭环收敛，场景时钟恢复推进。**

去重的必要：同一时刻重复触发同一动作会产生重复方案与重复审批单。实现上以「告警
+ 方案类型 +
故障链路」为幂等键------同一告警已存在同类型待审批方案时，ACT-03
不再重复生成。

  -------------- -------------------------- ----------------- --------------------------

## 5.4 任务与链路的新增

输入框新增任务：写入 comm_task（duration_min、initial_demand_gbps
等），同时生成 comm_demand 首条记录（valid_from_min =
当前分钟，valid_to_min = 当前分钟 + duration_min）与 comm_task_link
首条归属行。新增后触发 ACT-02，若目标链路容量不足则进入 ACT-03
方案流程。

输入框新增链路：写入
comm_link（容量、预警线、状态、平均修复时间、备用链路）。新增后触发
ACT-02，该链路以 0 占用进入资源池，可被后续切换或回迁选用。

## 5.5 任务归属

任务归属不覆盖、只追加：comm_task_link 以 (task_code, assigned_min)
为联合主键，每次切换插入新行。当前归属取 assigned_min 最新的一行，并与
comm_task.current_link_code
冗余同步。历史留痕同时服务于两个目的------T+120 全窗口证据检查，以及
ACT-06 定位「曾归属该链路」的回迁任务。

# 6. 时钟、挂起与审批超时

## 6.1 三种呈现与时钟行为

  **动作类型**       **呈现**                   **是否阻塞**     **时钟行为**
  ------------------ -------------------------- ---------------- ------------------------------
  ACT-01             告知型弹窗                 否（可关闭）     继续推进
  ACT-02 / 05 / 06   顶部提示条                 否               继续推进
  ACT-03 + ACT-04    模态框 + 60 秒决策倒计时   占屏，但不停表   场景时钟照常实时推进，不挂起

实时模式下不再有「挂起」：真实时间不会因为系统弹窗而停顿。60
秒倒计时的含义是人工决策时限------在这 60
秒内必须做出决定，到期未决定则由系统按保守默认执行。由于前瞻提前量（30
分钟）远大于决策时限（60 秒），人工永远有充足余量，不会出现「已经跑到
T+60 了审批才点下去」的时序错乱。

## 6.2 四路分支与超时兜底

> 模态框弹出 → 倒计时 60 秒开始走秒
>
> ├─ 点击「批准 REROUTE」 → 执行，decision_source = 人工
>
> ├─ 点击「批准 REPAIR」 → 标记批准，等待修复完成
>
> ├─ 点击「拒绝」 → 维持现状，持续预警监测
>
> └─ 倒计时归零 → 自动执行 is_default = 是 的方案
>
> approver = SYSTEM
>
> decision_source = 超时自动
>
> reason = 「60 秒未决策，自动执行保守默认方案」

UI 要求：保守默认方案卡片显示「保守默认」徽章与「60
秒未决策将自动执行此方案」副文案；倒计时同步显示数字与进度条，最后 10
秒高亮。超时自动执行必须写入审批记录与事件流水，供 T+120 证据核对。

## 6.3 等待期间的外部输入

等待人工决策的 60
秒里，场景时钟在真实推进，输入框也照常接收信息。修理单回执、新的事故等外部输入到达后立即触发本体判定，实时刷新模态框内的方案可行性（例如
repair 方案被作废、reroute
变为唯一推荐），但倒计时不重置------人工仍须在 60
秒内决策，否则走保守默认。

# 7. 保守默认策略

**本场景保守默认定为方案 A：PLAN-L-1H-REROUTE（转备用链路
L-3H），comm_plan.is_default = 是。**

  **理由**         **说明**
  ---------------- -----------------------------------------------------------------------
  风险是确定性的   T+50 的 11G \> 10G 是确定性超限，不是概率风险，等待即意味着必然发生
  时间没有余量     修复 L-1H 需 30 分钟，T+20 发起恰好落在 T+50 需求翻倍临界点上，零缓冲
  符合备用定位     L-3H 本就是为「资源紧张、无法分配」准备的场景，此刻正是启用条件
  备用可以归还     修复完成后由 ACT-06 自动回迁并释放，备用资源不会长期占用

若组织策略是「备用资源极度稀缺、非最后关头不动用」，只需把保守默认标记改到
repair 方案上，无需改动任何判定代码------该策略以数据（is_default
字段）表达，而非硬编码。

# 8. 回迁与备用释放

> 输入框输入「线路 1 修好了」
>
> ↓ Agent 意图识别 → link_restored {link: L-1H}
>
> ↓ 校验 L-1H.oper_state = up
>
> ↓ 查 comm_task_link：曾归属 L-1H 且当前不在 L-1H 的任务 → T-A
>
> ↓ 容量校验：回迁后 L-1H predicted = 3G ≤ 10G，通过
>
> ↓ ACT-06 执行：插入归属行（note = L-1H 修复完成，由 L-3H 回迁）
>
> ↓ 更新 comm_task.current_link_code = L-1H
>
> ↓ 释放 L-3H：重算占用 = 0G，无任务承载即归还资源池
>
> ↓ ACT-02 全局重算 + 递归判定 → 无新状况，闭环收敛
>
> ↓ 顶部提示条告知，不弹窗、不挂起、不需审批

回迁前提校验失败的处理：若 L-1H
已恢复但容量不足以容纳回迁任务，则维持任务在备用链路上的现状并告警，不强行回迁。备用释放不设独立字段------「该链路当前无任何任务承载且占用为
0」即为已释放，由占用重算自然得出。

# 11. 边界与异常处理

  **边界场景**                         **处理**
  ------------------------------------ ------------------------------------------------------------------------------------
  前瞻窗口内同时存在多个超限点         取最早命中的检查点作为告警的 predicted_min，方案按该时刻计算
  多个方案同时标记 is_default          以 generated_min 最新者为准；ACT-03 保证只标一个
  人工在倒计时内反复切换选择           以最后一次提交为准，倒计时不重置
  倒计时归零瞬间人工同时提交           以人工决策优先，取消超时自动分支，decision_source 记为人工
  repair 方案已批准但工单迟迟未回执    设工单等待超时（建议 5 分钟），超时升级为 reroute 并重新推送审批
  回迁时原链路容量不足                 维持现状不回迁，告警并保持备用链路占用
  同一告警重复触发 ACT-03              以「告警 + 方案类型 + 故障链路」为幂等键，已存在待审批同类型方案则不再生成
  新增任务的初始链路不存在或容量不足   登记时校验；不存在则拒绝，容量不足则登记后进入 ACT-03 方案流程
  新增链路编码重复                     拒绝登记并提示；comm_link.link_code 为主键
  输入文本无法识别类别                 返回识别失败并要求人工选择输入类别，不猜测、不默认执行
  预订事件的生效时刻已过               登记时即视为即时事件立即兑现，不进入待兑现队列
  场景分钟与真实秒                     实时模式下两者 1:1 同步：60 秒倒计时正好对应场景推进 1 分钟
  预测超限点距当前不足 60 秒           提前量盖不住决策时限，转 R3 硬约束：当前占用一旦真实越限立即重新生成方案，不等人工
